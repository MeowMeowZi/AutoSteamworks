# Steam 商店内容规则（给 AI 和人看）

这个游戏项目用 AutoSteamworks 把本地文件同步到 Steamworks 后台。
**分工**：AI 负责配置和写本地文件；人在 AutoSteamworks 网页（桌面快捷方式，或运行 `autosw`）上查看改动，再勾选上传。

## AI 必须遵守

1. **只改本地文件，不碰后台。** 不要运行 `push`、`assets`、`build`、`pull`、`login`，也不要自己打开 Steamworks 网页。需要拉取或上传时，请用户在网页上点按钮。`check` 和 `sort-images` 只动本地文件，可以运行。
2. 只改这些文件：`steam.config.yaml`、`STEAM_RULES.md` 末尾“本项目的风格”一节、`apps/<app>/store/`、`apps/<app>/assets/`。不要改 `.autosw/`（快照、上传记录、登录信息）。
3. **不要编造事实**：appid、depot id、价格、发售日期、奖项、评测和评分、硬件需求、构建账号都不能猜。在项目里找不到就问用户，或者先留空、在总结里列出来。
4. 不要在 yaml 里新增 key，也不要删 key（删掉 key 表示“不再同步这个字段”，不是“清空”）。要清空就把值改成空字符串 `""`。
5. 只改用户要求的语言和字段。翻译以 `english` 为准，用户另有说明时除外。各语言的译法按下面的术语表统一。
6. 改完运行检查，把报出的错误修掉：
   - 全局安装的：`autosw -c steam.config.yaml check`（整理图片是 `autosw -c steam.config.yaml sort-images`）
   - 网页的“AI 规则”页复制出来的提示里有本机可用的完整命令，以那个为准。
7. 最后给用户一份总结：改了哪些文件；哪些内容需要用户确认或补充；接下来要在网页上做什么，例如“拉取”或“上传”。

## 工作流程

### 第 1 步：确认现状

- 读 `steam.config.yaml`，记下各 App 的 key、appid 和语言。
- 看 `apps/<app>/store/_common.yaml` 是否存在。**不存在说明还没从后台拉取过**：请用户在网页上点“从后台拉取”，拉取完再继续写商店文本。没拉取就不知道后台有哪些字段，不要自己创建 store 目录。
- `steam.config.yaml` 不存在时，请用户在网页的“项目”页添加这个文件夹并初始化。初始化需要 appid，appid 在 Steamworks 后台 App 名称旁边。

### 第 2 步：从项目里收集资料

在游戏项目里找这些信息，并记下来源：
- 游戏名、简介、玩法、卖点：README、策划或设计文档、宣传文案、旧的商店文本、itch.io 页面草稿等。
- 引擎设置里的产品名、公司名：Unity 在 `ProjectSettings/ProjectSettings.asset`（productName、companyName）；Godot 在 `project.godot`；Unreal 在 `Config/DefaultGame.ini`。
- 本地化表或翻译文件：用里面已有的术语译法。
- 游戏导出目录，例如 `Builds/`、`Export/`、`bin/`：配置构建时要用。
- 可以用作宣传图和截图的图片。

### 第 3 步：填写“本项目的风格”

根据第 2 步的资料，填好本文件末尾的一句话介绍、目标玩家、语气和术语表。拿不准的写上“（待确认）”，并在总结里请用户确认。以后写任何文本都按这一节来。

### 第 4 步：写商店文本

建议的顺序：简短描述 → 关于此游戏 → 抢先体验问答（如果是抢先体验）→ 版权声明 → 系统需求 → 其他语言的翻译。各字段对应的文件见下面的“商店文本文件”。

准备整套资料或用户要求核对基本信息时，按“平台、系统需求、支持语言与玩家数”为当前 App 提出有依据的候选；系列按项目选填。只做文案或翻译时跳过这些项目。

准备整套商店资料或用户要求填写控制器支持时，按下文“控制器支持向导（v1）”逐题取证并自动填写本地答案；用户只要求改文案或翻译时不动向导。

准备整套资料或用户要求选类型、打标签时，按“类型与标签向导”填写相应类型字段、生成排序后的标签核对单；只改文案或翻译时跳过。

准备整套资料或用户要求核对内容调查时，按「内容调查填写建议」逐题整理项目和构建证据，生成本地核对单。仅做文案或翻译时跳过。

### 第 5 步：整理图片

准备整套资料或用户点名相应资产时，按下文「截图资产」「库资产与徽标放置」「客户端图片与图标」准备当前 App 的文件和逐项填写清单。按配置里的实际资产目录操作。只请求其中一项时，只处理那一项。

先找项目里已有的合格成品。库资产和客户端图标也可从正式美术源文件按下文规格导出。保留项目原件，只把需要整理的商店图、库图或主截图的副本放进 `待分类/`，再运行 `sort-images`。
- 位置按尺寸判断，尺寸表见下面的“图片”一节。920 x 430 默认算商店形象图片；要当库形象图片用，文件名里写 `library`。比 1920 x 1080 大的图片，文件名里写 `screenshot` 就算截图。
- 语言看文件名，例如 `header_english.png`、`capsule_schinese.png`。缺少语言线索时工具取 `english`，未配置英语时取该 App 的第一种语言。
- 先加 `-n` 演练一遍，看看每张图会放到哪里，再正式整理。同一位置原来的图会被挪到 `assets/已替换/`。

缺哪些位置，就在总结里列出来。图标和本地化截图变体使用下文指定的位置。

### 第 6 步：检查和总结

运行第 6 条规则里的检查命令，修掉错误，然后按第 7 条写总结。

## 配置文件 steam.config.yaml

路径都相对于配置文件所在的目录。网页的“设置”页也能改其中一部分。

```yaml
browser:
  channel: msedge            # 不要改，除非用户要求（可选 msedge / chrome）
  # profileDir: ...          # 登录信息目录，不要改
partner:
  delayMs: 1500              # 后台请求间隔，不要改
store:
  ignoreFields: []           # 不想同步的字段 name，支持 * 通配，例如 "app[content][sysreqs][mac]*"
languages: [english, schinese]   # 所有 App 默认同步的语言（Steam 语言 API 名）
steamcmd:                    # 只有上传构建时才需要
  path: steamcmd             # 不在 PATH 里就写完整路径；问用户
  user: <构建账号>            # Steam 构建账号的用户名；必须问用户，不要猜
apps:
  game:                      # App 标识：小写字母、数字、- 和 _
    appid: 1234560           # 必须来自用户或后台，不要猜
    name: 游戏名
    # languages: [english]   # 这个 App 单独的语言，不写就用上面的 languages
    assets:
      screenshotsAllAges: true   # 截图是否适合所有年龄。必须由用户确认，不确认就不要写
    build:                   # 上传构建用，可选
      setLive: beta          # 构建完成后设为哪个分支，不能是 default
      depots:
        - id: 1234561        # depot id，在后台“SteamPipe → Depots”里，问用户
          contentRoot: builds/windows   # 游戏导出目录
          exclude: ["*.pdb"]
  demo:                      # 有 Demo、原声带 DLC 时照这个格式加，appid 问用户
    appid: 1234570
    name: 游戏名 Demo
```

改了 `languages`，或者新加了 App，都要请用户在网页上重新“从后台拉取”，新语言和新 App 的文件由拉取生成。

## 商店文本文件

```
apps/<app>/store/
  _common.yaml                     和语言无关的字段，key 是后台表单字段名
  <语言>/short_description.bbcode   简短描述（商店页顶部、搜索结果里显示的那段）
  <语言>/about.bbcode               关于此游戏（长文本）
  <语言>/sections.<n>.content.bbcode   自定义区块的内容（标题在 _fields.yaml 的 sections.<n>.label）
  <语言>/earlyaccess.*.bbcode       抢先体验问答：why 为何采用抢先体验、how_long 大约持续多久、
                                   full_version 完整版有何不同、current_state 现状、
                                   pricing 价格是否变化、community 社区如何参与
  <语言>/legal.bbcode               版权和商标声明
  <语言>/_fields.yaml               该语言的其余字段：sysreqs.<系统>.<min|rec>.<processor|graphics|osversion|soundcard|notes>（系统需求文字）、
                                   awards.short（奖项）、reviews.<n>.quote（评测引语）、app.broadcast.title_custom（直播标题）
```

`_common.yaml` 里常用的 key：
- `app[name]` 产品名称
- `app[content][links][website]`、`[discord_server]`、`[youtube]`、`[twitter]`、`[privacy_policy]` 等是各种链接；`app[content][support_info][email]` / `[url]` 是客服邮箱和网址
- `app[content][sysreqs][windows][min][memory][amount]`、`[units]`（MB / GB）是内存；`[diskspace]` 是存储空间
- 以 `[=值]` 结尾的 key 是复选框，值是 `true` / `false`
- 开发者、发行商（`app[game][developers]…`、`app[game][publishers]…`）在后台是用搜索框选的，**不要改**
- 平台、系统需求、支持语言、玩家数与系列按下文核对与确认；类型与控制器按各自的向导规则填写。不要顺带改其他功能选项。

语言名用 Steam 的 API 名：`english`、`schinese`（简体）、`tchinese`（繁体）、`japanese`、`koreana`、`german`、`french`、`russian`、`spanish`、`latam`、`brazilian` 等。

## 平台、系统需求、支持语言与玩家数

按 App 和计划发布的构建版本核对，不把本体、Demo、DLC 的能力视为相同。**先出候选，再改字段**：按“项目｜已有值 → 建议值｜依据（文件路径、构建或测试记录）｜待确认问题”列出差异，让用户补充或确认。没有证据是“待确认”，不是“不支持”；保留已有选择，不把“待确认”写进商店。用户确认后，只写本地已拉取且适用于这个 App 的字段。后台字段与本节不符时不猜 key。

### 支持平台

- 先查该 App 的 `build.depots[].contentRoot` 和排除项，再查实际导出的游戏包。要能指出**玩家启动的游戏程序**：例如 Windows 游戏主程序、macOS 游戏 `.app` 里的主程序、Linux 原生游戏可执行文件。目录名、引擎勾选的目标、打包工具或第三方库都不能单独作为证据。
- 平台候选对应 `_common.yaml` 的 `app[platforms][win|mac|linux|android]`（四选项可多选）。Windows 包能通过 Proton 运行不等于提供 Linux 原生包；普通手机 APK 不等于支持 Steam Frame，只有面向其独立运行的 VR 构建才列 Android 候选。没找到包不默认选 Windows，也不取消原有平台；询问构建在哪。
- 平台、下文的语言及玩家数在已核对表单中是隐藏文本字段。新增勾选用字符串 `"true"`，明确确认取消才写 `""`；已有 `"1"` 等肯定值不为统一格式而重写。不要误用 YAML 布尔值。

### 最低配置与推荐配置

- 每个已确认平台单独做两栏草稿：最低（`min`）和推荐（`rec`，可不填）。列明构建能证实的事实，如程序架构、实际打包启用的渲染后端、该平台安装内容大小。安装体积按玩家要安装的内容统计，不用压缩包大小、整个工程大小或所有平台之和。64 位不等于某个最低系统版本；启用了某个图形 API 也不等于测过某款显卡。
- 硬件档位看发布构建的实测记录：哪台机器、什么分辨率与画质、哪个有代表性的重负载场景、帧率或帧时间和内存峰值。依据项目设定的体验目标分别判断两档。只有一台开发机、编辑器预览、限核/限内存模拟或引擎默认值时，只报告观察结果；不要推算最低或推荐 CPU、GPU、内存。缺证据的不填，不抹掉原值。
- 确认后，系统版本、处理器、显卡、附注等文本写到相应商店语言的 `_fields.yaml`，例如 `sysreqs.windows.min.processor`。内存、磁盘的数值和单位在 `_common.yaml` 成对填写，例如 `app[content][sysreqs][windows][min][diskspace][amount]` 和对应的 `[units]`。注意平台开关叫 `win`，系统需求叫 `windows`。只改已有的字段和有效单位，不顺手填写宽带、DirectX 或 VR 要求。

### 支持语言

列出“游戏语言｜界面｜字幕｜完全音频｜证据”。`steam.config.yaml` 的 `languages` 是**商店文本同步语言**，不用于推断游戏支持，也不要反过来自动改它。三列分别核对：
- **界面**：发布版实际能切换或按系统语言加载，菜单、UI 和游戏文本有可用翻译；空语言包、占位符、回退到英语或仅有商店介绍都不算。
- **字幕**：核对对白字幕表、过场字幕和包内覆盖范围，不把菜单译文当字幕。
- **完全音频**：核对所有语音对白是否都有该语言的配音并随构建提供；个别配音或预告片配音不算。没有语音对白不自动勾完全音频，也不批量勾所有语言。

确认后按 Steam 语言名填写 `_common.yaml` 已有的 `app[content][supported_languages][<语言>][supported|subtitles|full_audio]`，后三个选项依次对应界面、字幕、完全音频。资料没覆盖的列留待确认，不清除已勾选项。

### 玩家数

从可玩入口、关卡规则、联机/本地加入流程或测试记录判断玩家如何一起玩。**单人和多人可以同时成立**；不默认单人。只有排行榜、云存档、联网 SDK 或机器人对手，不能证明支持真人多人。
- `_common.yaml` 中以下编号指 `app[classification][category][category_N]`：单人 2，多人 1。选多人时至少确认一种模式；对每种模式，分别确认至少一种可用方式，不把合作的连接方式套给对战。
- 玩家对战 49：在线 36、局域网 47、本地 37。合作 9：在线 38、局域网 48、本地 39。例如同机双人合作应列出“多人 → 合作 → 本地”，不因此选在线合作或局域网合作。缺模式或方式时先追问，不只填一个“多人”。
- 本地对战或本地合作变化时，同时核对共享/分屏汇总项 24；后台界面还会联动远程同乐 44，**不把它当作已测试的在线多人能力**，不替用户改其独立选择。跨平台、大型多人在线等也需独立依据。上传时提醒用户一起核对父项、模式和方式，并与玩家人数标签对照。

### 系列（按项目选填）

不设全局系列，不沿用开发者或发行商名称。只有项目资料明确给出正式系列名或用户指定时，才建议填写已拉取的系列名称字段，例如 `app[game][franchises][0][name]`；不凭相似标题、续作编号或共同开发者推断。没有系列就留空，已有名称不覆盖；不要为占位另建系列或新增字段。

## 控制器支持向导（v1）

以下顺序和字段按 2026-11-19 的 Steamworks「商店页管理 → 基本信息 → 支持控制器」核对。记录的是**题目与判断规则，不是各游戏共用的答案**。范围是桌面和大屏幕模式；VR 输入设备另写在系统需求。

| 步骤 | AI 如何按当前 App 的项目证据作答 |
| --- | --- |
| 1 · 通用输入 | 从发布版启用的输入方案、游戏内提示和设计说明，区分「仅键鼠」「键鼠和手柄均可」「均可但推荐手柄」「必须手柄」。推荐或必须要有直接依据。明确仅键鼠就直接跳到第 5 步；没搜到手柄配置不等于仅键鼠。 |
| 2 · Xbox | 全部适用条件都满足才选完全支持：只用手柄可经过启动器、菜单、设置、游玩到退出；按键提示图标正确；需输入文字时能调出屏幕键盘；如有本地多人，支持多个控制器。已确认能用手柄，但有明确例外（如暂停菜单必须用鼠标），选部分支持。只有移动或战斗的按键绑定不足以判为完全支持。 |
| 3 · PlayStation | DUALSHOCK 和 DualSense 分开判断。每款都要能完成 Xbox 手柄可做的操作并显示对应图标，再按证据选 USB 或 USB + 蓝牙；USB 可用不代表蓝牙可用。两款都明确不支持才选「均不支持」。不要把模拟成 Xbox 输入当成已验证的 PS 支持。 |
| 4 · Steam 输入 API | 核对发布版是否实际使用 Steam Input 动作、查询动作来源来显示正确图标、断连自动暂停，并支持从 Steam 配置器改键。引用了 Steamworks SDK 或普通引擎手柄映射不等于完整集成。 |
| 5 · 概要 | 在总结里按 App 列出走过的分支、答案及依据（文件路径、测试记录或用户确认）；仅键鼠时将第 2–4 步列为“不适用”，不要追问。 |

**填到哪里：**只改从后台拉取的 `apps/<app>/store/_common.yaml` 中这组字段。下表的 `category_N` 指完整 key `app[classification][category][category_N]`。这些字段是字符串：肯定写 `"true"`，否定写 `""`，不是 YAML 布尔值。

| 根据哪个答案写 | 字段及取值 |
| --- | --- |
| 第 1 步 | 仅「推荐手柄」置 `category_60`；仅「必须手柄」置 `app[content][keyboardmouse][notice]`。其余情况两者均空。仅键鼠时，第 2–4 步的字段也全部为空。 |
| 第 2 步 | 部分支持置 `category_18`，完全支持置 `category_28`，两者互斥。 |
| 第 3 步 | DUALSHOCK 的 USB / 蓝牙分别对应 `category_55` / `category_56`；DualSense 分别对应 `category_57` / `category_58`。USB + 蓝牙要同时置该型号的两个字段；不支持的型号两个均空。 |
| 第 4 步 | 完整集成置 `category_59`，明确不符合则为空。 |
| 第 5 步 | 全部适用题都有答案才置 `app[content][controllertagwizard][v1]` 为 `"true"`。不要只改完成标记。 |

先在内存中算出整组答案，只写有差异的值。任一适用题证据不足，或新答案和已有的已确认答案冲突，暂不改整组字段，只问具体缺哪项。未拉取、有效字段缺失或向导版本不符时也不要补 key 或套用旧映射。Demo 按其自身构建和已拉取字段核对。提醒用户上传时一起勾选本组改动；AI 不操作后台。

## 类型与标签向导

2026-11-19 核对了游戏商店「基本信息」中的两套控件。**类型**是普通商店表单的分类；**标签**是独立向导里有先后顺序的词。即使同叫“动作”，也不能混用字段、ID 或提交方式。

### 类型：先多选，再定一个主要类型

- 先用一句话写清楚玩家反复在做什么。从当前版本的核心玩法、可玩模式、截图和设计资料中找依据，选能描述这款游戏的类型，再从**已选类型**里挑一个最能代表它的作为主要类型。例如“含装备升级”本身不能证明游戏是角色扮演。
- 对照已拉取的 `apps/<app>/store/_common.yaml`。本次普通游戏表单可见的 `rgGenres[编号]` 为：动作 1、冒险 25、休闲 4、独立 23、大型多人在线 29、竞速 9、角色扮演 3、模拟 28、体育 18、策略 2。选中写字符串 `"true"`；确认取消才写 `""`。不要改其他应用类型的隐藏选项或 `rgGenres[sentinel]`。
- `app[classification][primary_genre]` 写选中类型的编号字符串，例如主要类型为策略时用 `"2"`，对应 `rgGenres[2]` 必须已选。缺字段、选项不符或和已有确认值冲突，就提出具体问题，不自行新增或清空。后台下拉框随多选项生成：若主要类型是新勾的，提醒用户先上传新增的类型，重新核对后再上传主要类型。

### 标签：按实际向导选词，再统一排序

从“为我的作品打上标签”进入后，起始页先展示已有标签。AI 不打开后台：按下面顺序在本地替当前 App 选词，从工具安装目录的 `templates/steam-tags.zh-CN.txt` 查正式名称（“复制给 AI”会给出完整路径）。这是核对当日的词表；若和当前向导不符，以向导为准。现有商店描述、玩家标签和平台推荐只能用来找候选，不能替代项目证据。

| 向导顺序 | 怎么选 |
| --- | --- |
| 1 主类型 → 2 类型 → 3 子类型 | 从宽到窄：核心玩法属于哪一大类、属于哪一玩法家族、哪种细分最能区分它。这里的“主类型”是**标签**，可多选。当前问卷校验分别为 1–3、0–5、0–6 个；不为凑数选满。 |
| 4 视觉效果与视角 | 看实际游玩画面和镜头，而不是宣传图。例如“像素图形”和“俯视”分别说明画风与视角。 |
| 5 主题与气氛 | 看贯穿游戏的世界观、叙事和体验，不因一个场景或角色就给整个游戏贴标签。 |
| 6 特色 | 看玩家会反复使用的机制，例如“牌组构建”或“资源管理”。只在路线图、未启用插件或测试代码中出现的不选。 |
| 7 玩家人数 | 以可玩的模式为准，区分单人、本地合作、在线合作等，与商店页的玩家数声明核对。排行榜不是多人玩法。 |
| 8 还有什么？ | 复核从商店描述提取或手动搜索的补充词。只补前面遗漏且有依据的正式标签；同名词最终只排一次。 |
| 9 用户标签 | 有现成社区标签时逐项复核。准确的保留；明显不符的单列为“建议移除”，说明理由，由用户确认。没拿到现有列表就写“未提供”，不假设它为空。 |

没有候选的题组向导会跳过。最后进入**检查与排序**，可参考建议优先顺序和相似游戏，但最终按本作的代表性排序。前 5 个合起来应让玩家知道实际玩什么，具体子类型、关键机制通常比“独立”等泛词有区分度。上线至少要有 5 个准确标签，按权重取前 20；不必凑满 20。若连 5 个都无法证实，只给已确认项并说明还缺什么。[Steam 标签说明](https://partner.steamgames.com/doc/store/tags?l=schinese)

**交付：**为本体或有独立标签向导的 DLC 在各自商店目录下写 `_tags.md`（本地核对单，不是上传字段）：按题组列候选与取舍，再给一张“排名｜正式标签名｜项目依据（文件路径、构建画面或用户确认）”表；已有名单可比对时标明新增、调序及待确认的移除项。证据不足的词放表外；找不到的词不要造。Demo 沿用本体标签，不为它另做一套排名。

看到「已应用 0 个标签」或不足 5 个时，先从已有 `_tags.md` 核对本次构建，再补齐有证据的候选。把最终建议的前 5 个正式名称按顺序列在核对单开头，便于在向导中逐项录入。后台已应用数量与本地建议分开记录。

**应用：**类型可以走普通商店文本上传，标签排名不行。不要在 `_common.yaml` 新造 `tags[]`、权重或完成标记。用户按核对单在向导里选词、拖动排序，在最终确认框核对前 20 和可能移除的社区标签，再决定是否点“发布”。标签独立发布，不会随普通商店草稿一起上传或发布。

## 内容调查填写建议

准备整套资料或单独核对内容调查时，为当前 App 的目标构建生成一份供用户逐题核对的建议。范围是本地分析，即使用户确认了某个答案，也只更新建议。不要打开问卷、填写或保存草稿、确认栏目、生成或发布分级，也不要把建议写入任何商店同步字段。

### 从哪里取证

- 先标出 App、构建版本或日期、实际检查的 depot 和资源包。结合 `build.depots[].contentRoot`、打包清单和排除项，核对剧情对白、各语言文本、美术、音视频、关卡与交互配置。成人内容要覆盖随包分发但正常游玩无法访问的资源。只存在于工程的原型或删减素材，先核对是否打进包。本体、Demo 和 DLC 按各自交付的内容判断。
- 区分提及、画面描绘、玩家可参与，以及出现频率和表现强度。文件名、标签、单张截图或关键词可以帮助定位，仍需查看对应内容。没有构建、资源无法读取、素材来源不明、证据矛盾或覆盖不足时，相关答案留空，向用户问一个能解决问题的具体问题。
- AI 首题还涉及商店页、社区资产和营销材料。核对成品素材来源、制作记录或作者确认，区分预先生成和游玩时实时生成。仅发现开发辅助工具、AI 插件或依赖，无法判断交付内容的来源。

| 「上传时将快捷方式转换为应用图标」 | 两项使用同一设计且透明区域变为纯黑后的预览合适时，建议勾选并复用快捷方式图标。需独立底色或设计时，建议取消勾选并选用单独的 JPG。已有独立应用图标时先核对是否应替换。 |

在 `_assets.md` 标出每个图标的源文件、交付路径、尺寸和转换选项。缺正式源图或背景色有歧义时列为待确认。客户端图标有独立上传入口，放在 `client-icons/` 可避免被商店图片整理命令误分到其他位置。

## Steam 的硬性规则

- **简短描述**：后台标注长度为 200-300 个字符，超过 300 会标红（`check` 会检查）。开头就说清楚玩法，不要只写剧情。不要用 BBCode 标签。
- 文本用 **BBCode**，不支持 HTML 和 Markdown。常用标签：
  `[h1] [h2] [h3] [b] [i] [u] [strike] [url=https://…]文字[/url] [list][*]…[/list] [olist][*]…[/olist] [hr]`
  标签要成对闭合（`[*]`、`[hr]` 除外）。BBCode 没有注释语法，写进文件的内容都会显示在商店页上。
- “关于此游戏”里的图片要先在后台上传，再用后台生成的 `[img]{STEAM_APP_IMAGE}/extras/…[/img]` 引用，不能直接用外部图片地址。AI 不要自己写 `[img]`，哪里适合配图写在总结里告诉用户。
- 不能放其他商店（Epic、itch.io 等）的链接，也不能引导玩家到站外购买。
- 基础宣传图只能有游戏美术、游戏名称和官方副标题，不能有评测引语、奖项、“特价”之类的文字。
- 截图必须是游戏的实际画面，不能用概念图或宣传图。
- 不要写无法证实的比较，比如“最好玩的”“第一款”；没有授权的评测和奖项不要引用。
